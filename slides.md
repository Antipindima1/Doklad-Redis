# Кэширование, инвалидация, персистентность и Redis

Выполнил Антипин Д.А.

---

## Что такое кэширование?

- Кэширование — метод оптимизации хранения данных максимально близко к месту их использования.
- Цель: уменьшить задержки и снизить нагрузку на серверы и БД (устранение узких мест).
- **Первый запрос:** сервер берёт данные из БД и сохраняет их в кэше.
- **Повторный запрос:** данные извлекаются напрямую из кэша — быстро и дёшево.

---

## Внешний кэш и стратегия Cache-Aside

Внешний кэш (например, Redis) — отдельное хранилище, доступное всем экземплярам приложения.

1. Приложение запрашивает данные из Redis по ключу.
2. **Cache Hit** — данные найдены и сразу возвращаются клиенту.
3. **Cache Miss** — запрос в основную БД.
4. Данные из БД сохраняются в Redis с заданным TTL.
5. Данные отдаются клиенту.

---

## Инвалидация кэша: как поддерживать актуальность

Инвалидация — процесс удаления или обновления устаревших данных.

- **TTL** — автоматическое устаревание через интервал времени.
- **Событийная инвалидация** — очистка при операциях изменения данных.
- **Версионирование** — уникальный идентификатор для каждой версии данных.
- **Polling** — периодическая проверка основного источника.
- **Pub/Sub** — подписка на уведомления об изменениях.

Виды: ручная (удаление ключа после обновления в БД) и событийно-ориентированная (Kafka/RabbitMQ).

---

## Персистентность (стойкость данных)

Персистентность — свойство данных выдерживать выключение, перезагрузку или сбой системы без потери.

- **В базах данных:** транзакция завершена, когда данные записаны на диск (Durability в ACID).
- **В кэш-системах (Redis):** данные в RAM, персистентность — через RDB (снимки памяти) и AOF (лог команд).
- **В ООП:** способность объектов сохранять состояние между запусками программы.

---

## Redis: Remote Dictionary Service

- Высокопроизводительная нереляционная (NoSQL) СУБД с открытым исходным кодом.
- Хранит данные в оперативной памяти по принципу «ключ — значение».
- Поддерживает структуры данных: строки, хэши, списки, множества, сортированные множества.
- Обеспечивает молниеносную скорость доступа.
- Стандарт де-факто для внешнего кэширования в современной разработке.

---

## Redis в проекте: поиск автомобилей на карте

В каршеринге автомобили постоянно передают телеметрию: координаты, состояние замков, зажигание, пробег и уровень заряда.

- В системе одновременно работают тысячи автомобилей.
- Каждый автомобиль отправляет телеметрию с интервалом в несколько секунд.
- Пользователю нужно видеть актуальное расположение автомобилей на карте.
- При поиске система должна быстро находить автомобили в заданном радиусе.

**Почему не подходит обычная работа с БД:** PostgreSQL получает лишнюю нагрузку от постоянного обновления координат; TimescaleDB предназначена для временных рядов, а не для оперативного геопоиска.

---

## Почему именно Redis

1. **Работа в оперативной памяти** — быстрое чтение и обновление, меньше обращений к основной БД.
2. **Географический индекс (GEO)** — `GEOADD` добавляет автомобиль с координатами, `GEOSEARCH` находит автомобили в радиусе.
3. **Хранение актуального состояния** — последние полученные координаты, а не вся история перемещений.
4. **Разделение ответственности** — Redis: оперативное состояние и геопоиск; TimescaleDB: история телеметрии; PostgreSQL: основные бизнес-данные.

---

## Архитектура применения Redis в проекте

- Провайдер телеметрии → Telemetry Ingestion → Kafka → Обработчик телеметрии.
- Обработчик обновляет текущее состояние автомобиля в Redis и сохраняет исторические данные в TimescaleDB.
- При открытии карты выполняется географический поиск по данным Redis.
- Результат — список автомобилей поблизости и их отображение на карте.

## Как хранятся данные в Redis

| Элемент | Пример | Назначение |
|---|---|---|
| Идентификатор автомобиля | car_id = 125 | Определяет автомобиль |
| Координаты | 55.751244, 37.618423 | Последнее известное местоположение |
| Состояние замков | locked = true | Техническое состояние замка |
| Зажигание | ignition = false | Состояние зажигания |
| Пробег | mileage = 45210 | Последнее значение пробега |
| Уровень заряда | charge = 78 | Уровень заряда аккумулятора |
| Время события | timestamp | Время получения телеметрии |

Для геопоиска используется GEO-индекс Redis (`GEOADD`, `GEOSEARCH`). Актуальность контролируется TTL или проверкой временной метки последнего события.

---

## Минусы и трудности применения Redis в проекте

- **Устаревшие координаты.** Автомобиль перестал передавать телеметрию, а координаты остались. Решение: хранить метку времени, использовать TTL, исключать устаревшие данные из результатов.
- **Расхождение технического состояния и статуса бронирования.** Решение: не использовать Redis как источник истины для бронирования, проверять статус через Booking Service.
- **Недоступность Redis.** Решение: восстанавливать состояние из событий Kafka и исторических данных TimescaleDB, предусмотреть повторное заполнение.
- **Дополнительная инфраструктурная сложность.** Решение: контролировать объём памяти, настроить мониторинг, разделить ответственность между Redis, PostgreSQL и TimescaleDB.

---

## Рекомендации: когда использовать Redis

| Когда использовать | Когда не использовать |
|---|---|
| Кэширование часто запрашиваемых данных | Как единственный источник истины для денежных операций |
| Хранение актуального состояния объектов | Для основных статусов бронирования без проверки бизнес-сервисом |
| Географический поиск и работа с координатами | Для больших объёмов холодных исторических данных |
| Счётчики и временные ограничения | Для сложных аналитических запросов |
| Хранение пользовательских сессий | Когда данные редко читаются и нет требований к скорости |
| Быстрый доступ к часто обновляемым данным | |

---

## 6 ключевых сценариев использования Redis

1. **Кэширование** — снижение нагрузки на БД (товары, профили, сессии).
2. **Управление сессиями** — масштабируемое хранение данных сессий в памяти.
3. **Таблицы лидеров и рейтинги** — сортированные множества для real-time обновлений.
4. **Очереди сообщений и Pub/Sub** — асинхронная коммуникация, фоновые задачи.
5. **Аналитика в реальном времени** — счётчики, HyperLogLog, битовые карты.
6. **Флэш-распродажи** — обработка пиковых нагрузок без падения БД.
